# netlib v0.17.4 — PF DNS lock: lockout and recovery fixes

Branch `private-all`, 2026-11-10. Fixes the findings of the lockout audit
(`docs/dev/AUDIT_PF_LOCKOUT_REPORT.md`, F1–F17). The design is unchanged: rules in the
child anchor `com.apple/foxhole.dnsleak`, `/etc/pf.conf` never edited, PF enabled by
reference token.

## Why

The audit found paths where DNS stayed blocked after the user tried to remove the lock,
or where the lock came back at the next boot although the session said it was off. The
worst one: the backup's `restore.sh` reported success and left the lock in place.

## What changed

### Recovery

- **F1 `restore.sh`:** always removes the lock: boots out the LaunchDaemon, deletes its
  plist, flushes the foxhole anchor, releases only our PF reference (token file), deletes
  the helper and rules file. The main ruleset is not touched. The lock state at backup
  time is deliberately not restored; re-enable it from the menu.
- **F2 `disable_pf_dns_lock`:** the anchor is flushed right after the boot daemon is
  removed, before the helper re-install, so a failed re-install cannot leave the block
  rules loaded.
- **F16 `reset_net_hardening`:** each of the three disables runs in a subshell; a failure
  in one no longer skips the others.

### Enable

- **F3, F4 `enable_pf_dns_lock`:** the helper's `start` and `status` run synchronously
  before the boot daemon is installed (the status poll loop is gone). If the start fails,
  or the daemon cannot be installed or bootstrapped, the lock is rolled back to "fully
  off": no plist, no rules, no PF reference of ours. `_install_pf_launchdaemon` now
  returns 1 on failure instead of only warning. Enable waits for the daemon's first run
  and checks `status` once more before it reports ACTIVE. A mode switch with the lock already on
  reloads the anchor synchronously, so the kernel never keeps the old mode while the
  message says ACTIVE.
- **F5 mode switch:** `prepare_pf_dns_lock_anchor` writes
  `/etc/pf.anchors/com.hardening.dnsleak.new`. `enable_pf_dns_lock` moves it over the live
  rules file only after the confirmation and the `com.apple/*` guard, and deletes it when
  the user declines or the guard refuses. A declined switch can no longer take effect at
  the next boot.
- **F13 menus:** a failed enable prints a warning and the menu stays open
  (`mac-hardening-netlib.sh`, `vpn_daily.sh`).
- **F6:** the enable prompt and `vpn_daily.sh` [4] say that captive portals and VPN
  clients that find their server by name need the lock off to connect.

### Helper (`/usr/local/libexec/foxhole-pf-dnslock`)

- **F11, F12 `start`:** a failed start never leaves block rules without a held PF
  reference: the anchor is flushed, and if the token file cannot be written the reference
  is released. When our reference is already held (the lock is active and this is a
  reload), a failed reload keeps the rules that are loaded.
- **F8 new `boot` action**, used by the LaunchDaemon: same as `start`, retried up to
  5 times 2 s apart (launchd does not re-run a failed `RunAtLoad` job). `start` and `boot`
  log a warning when the main ruleset has no `anchor "com.apple/*"`; `status` now fails in
  that case, because the lock is inert.

### No user-owned staging files (F14, F15)

The rules file, the helper, the LaunchDaemon plist and the legacy `pf.conf` rewrite are
streamed to a root-owned `*.new` file with `sudo tee`, then `chown`/`chmod`/`mv`. Before,
they were staged in a `mktemp` file owned by the invoking user, which another process of
that user could rewrite before root installed it. The only `mktemp` left in the netlib is
the hosts download in `update_hosts`.

### Other

- **F10 legacy `pf.conf` migration:** asks before the main-ruleset reload and says that
  it replaces a VPN kill switch's rules. The `restore.sh` header says the same.
- **F17 `vpn_daily.sh`:** offers a backup snapshot before the menu, like the netlib menu.
- `disable` message: "a reference is still held, by another program or a lost one of
  ours" (F12).

## Still open

- **F7:** the helper replaces the interface list at start instead of merging it with the
  list in the rules file. Changing it reverses decision D2 (T17 asserts the stale list is
  gone), so it needs a decision first.
- **F9:** the anchor's `quick` pass rules (ICMPv6, Quad9, `utun0–15`) may pre-empt a VPN
  kill switch's block rules. Needs a real kill switch (Mullvad) to confirm the rule order.
- Ownership of `/usr/local/libexec` is not checked before the helper is installed there
  (report section 2.5).
- `update_hosts`: a failed GitHub API call exits the script after the download (report
  section 5, note 9); its download still uses a user-owned temp file.
